# Replay corpus and independent review

The repository contains **100 complete candidate replays** in 20 families of
five reformulations. Each freezes the normalized task, restrictions, candidate
pool, host snapshot, catalog, two policies, synthetic prices/usage, expected
receipts, trace hashes and a proposed decision. Every human-validation flag is
false. Passing these fixtures establishes reproducible contract behavior, not
100 independently validated decisions or a measured model improvement.

## Artifacts

`tests/fixtures/evaluation/replays/candidate-001.json` through `candidate-100.json`
contain individually complete envelopes. `replay-manifest-v1.json` binds their
identities, splits, content/input hashes and expected traces.
`human-review-worksheet-v1.json` leaves reviewer, evidence and reviewed decisions
unfilled. The original `candidate-corpus-v1.json` retains objectives and sources.

`CandidateReplay::from_json(bytes)` checks the complete input binding and
recomputes receipts/traces. `replay()` returns both audited traces. Clocks are
fixed for repeatability; real routing needs current time and fresh evidence.
Use the full envelope for fallback cases: it also binds explicit unavailable
candidates beyond the inner `ReplayRecord`.

```sh
cargo test -p router-eval --test candidate_replays --locked
cargo run -p router-eval --example candidate_corpus --locked
```

The example compares generated bytes against existing fixtures. Passing
`-- --write` explicitly regenerates them. Changed input hashes invalidate any
review attached to the old inputs.

## Coverage and limits

The proposed split is 60 training, 20 validation and 20 held-out cases, without
family overlap. This partition still requires independent review. Cases cover
all three phases, three selected models, trusted/untrusted skills, unknown
capabilities and permissions, unsupported effort, budgets, write restrictions,
verification independence, equal-score abstention and fallback exhaustion.

Twenty out-of-domain cases cover cooking, travel, personal writing and finance.
Their pool is explicitly empty. Abstention verifies empty-pool behavior, not
automatic domain detection. Retrieval families test phase-level skill/pool
constraints, not BM25 recall. Workflow/prompt objectives likewise do not replace
DAG runtime or renderer tests.

The shadow candidate is a deterministic alternative weighting policy, not a
semantic-model invocation. Both traces keep transport, validation and functional
outcomes unknown. Prices and usage are synthetic; elapsed time is unknown. The
generator and replay call no model or external provider.

## Records from real runs

`agent-router feedback replay-export` builds a sealed `ReplayRecord` from an
executed run and labels it only from a recorded integration and verification, or
from a human verdict. It never labels from transport success, and it refuses a
rejected run because `CaseLabel` cannot express a candidate that is not
expected. The label is never independent, so these records do not replace the
review protocol below. Rules and limits: [local feedback](feedback.md).

## Human review protocol

1. Freeze artifacts, hashes, family split and review procedure before labeling.
2. Choose reviewers independent of candidate-policy authors. Establish their
   identities and preserve review evidence outside the generated corpus.
3. Review each objective and explicit context before its proposed decision.
   Check risk, scope, permissions, freshness, budgets and independence. Decide
   acceptable candidates or abstention. If the context itself needs correction,
   create a new input hash and review that version.
4. Fill the worksheet's reviewed decision, reviewer ID, independence and evidence
   hash. Set `human_validated=true` only after actual review. Generated proposals
   and passing tests cannot supply that attestation.
5. Create separate reviewed `ReplayRecord` values with supplied `CaseLabel`
   values. Preserve the original candidates. Labels enter the reviewed input
   hash; retain the original-to-reviewed hash mapping and evidence.
6. Pre-register metrics, thresholds, minimum cases/families, training-family
   exclusions and subgroup checks before held-out replay. No recall or gain
   threshold is invented by the project.

`compare_shadow` requires independent labels, matching held-out data,
pre-registered criteria, observed gain, no route-accuracy regression and zero
hard-constraint violations. Every metric guards against regression: a metric the
criteria do not list may not regress at all, and only an explicit rule's recorded
`maximum_regression_micros` allows a listed metric to regress. An unlisted metric
that cannot be measured (unknown outcomes, missing latency) blocks nothing and is
not reported: `ShadowReport` has no warnings list, and adding a serialized field
is a contract change left to a decision. A listed one blocks as
`promotion.metric_unknown.*`. Policy: ADR 0017
(`docs/adr/0017-bounded-retention-and-publish-durability.md`). Tests confirm that the generated held-out cases
cannot enable promotion. A passing evaluation is only evidence for the
[separate signed activation protocol](feedback.md).

Still unproven: actual independent review of the required cases, an agreed
retrieval threshold, held-out gain, and live shadow/canary results. Changing
status fields or closing issues cannot establish those results.

## Descriptive cohort metrics

`agent-router eval metrics --cohort cohort.json --records record-a.json record-b.json`
analyses sealed `ReplayRecord` observations. Add `--json` for the versioned
report. This command does not reroute historical inputs, contact a provider,
verify present host capabilities or change a promotion decision. A valid report
with missing evidence exits successfully and preserves the unknown values.

The cohort manifest fixes the complete set of cases:

```json
{
  "schema_version": 1,
  "analysis_authorized": true,
  "provenance": "synthetic",
  "cases": [{
    "case_id": "case-a",
    "input_hash": "<sealed ReplayRecord input hash>",
    "policy_id": "baseline",
    "policy_sha256": "<SHA-256 of the typed PhasePolicy JSON bytes>",
    "budget": {"max_cost_microusd": 100, "max_tokens": 1000, "max_elapsed_ms": 500},
    "predicted_success_micros": 700000,
    "usage_complete": false,
    "usage_evidence_sha256": null
  }]
}
```

`policy_sha256` uses the compact bytes from `serde_json::to_vec(&phase_policy)`
and `router_adapter_api::content_digest`; it is separate from the route receipt
policy hash. The input hash already binds prices, usage, outcomes and context.
The cohort hash covers its entire canonical manifest, with cases sorted by ID.
Records and manifest rows may be reordered without changing report bytes.
Duplicate, missing, extra or substituted records are refused before a report is
returned. The report contains aggregate data and hashes, without task text or
local file paths.

Provenance is `synthetic` or `supplied`. Authorization, usage completeness and
evidence hashes are caller declarations, not authenticated facts. Complete
usage requires a supplied evidence hash; this command does not read a file from
that hash. Empty usage gives zero cost only when explicitly declared complete.
Missing pricing or incomplete usage gives unknown cost, with separate counts.
Prices explicitly equal to zero remain known zero. Invalid model identities,
incoherent token counts and arithmetic overflow are errors.

| Report field | Definition |
| --- | --- |
| `success_at_budget` | Functional success with cost, tokens and recorded elapsed time within every explicit limit, including equality. Functional failure or a known overrun is failure. Otherwise unknown. Recorded partial tokens can prove an overrun, but cannot prove that a budget was met. |
| `success_at_budget_rate` | Exact successes / all cases, only when no cases are unknown. Lower and upper bounds remain available otherwise. |
| `cost_microusd_per_functional_success` | Costs of all cases, including failures, divided by functional successes. Unknown when any necessary cost/outcome is missing or no case succeeded. Cost is recalculated from supplied usage and prices, not a provider invoice. |
| `total_execution_ms_per_functional_success` | Sum of recorded case durations, including failures, divided by functional successes. Unknown with missing durations/outcomes or zero successes. This is not wall-clock workflow duration. |
| `calibration.brier` | Mean binary squared error `(p - y)^2`, where `y` is functional success and probability is an explicit integer from 0 to 1,000,000. |
| `calibration.ece` | Sum over ten fixed bins of `abs(sum(p) - successes)`, divided by all cases. Bins are lower-inclusive and upper-exclusive, except the last includes probability 1. |

Ratios retain integer numerators and denominators without rounding. Brier uses
probabilities squared in millionths; ECE uses millionths. Both global values are
unknown unless every cohort case has a prediction and known functional outcome.
Known-pair bins and missing counts remain visible; difficult cases are never
silently removed from the denominator. Ranking scores are not probabilities.
This report does not prove predictions were made before outcomes were known.

Inputs are limited to 1,000 cases, 1 MiB for the manifest, 4 MiB per record and
16 MiB of records in total. JSON rejects duplicate and unknown keys. Cost,
latency and token sums use checked arithmetic. A manifest hash identifies an
analysis definition; it is not an external trust anchor or preregistration proof.

The tradeoff report closes the descriptive regret and quality/cost frontier
calculation for supplied cohorts. First-plan acceptance, scanner false-positive
rates and persistent caching remain open. Synthetic fixtures establish the
calculations, not product gains or human evaluation.

## Comparable policy tradeoffs

`agent-router eval tradeoffs --cohort tradeoffs.json --records record-a.json record-b.json`
compares the recorded observations for 2 to 8 pinned policies over the same
exhaustive cases and per-case budgets. Each case fixes the policy selected for
regret analysis and carries exactly one usage-completeness cell per policy.
An incomplete observation stays in the denominator. Records must have the
same policy and observation key sets as the cohort; policy hashes bind the
serialized typed policies, not a route receipt. This input has no receipt for
the plan actually executed, so the report does not certify that any compared
policy produced an executed plan.
The provenance and usage evidence hashes are caller declarations; the command
checks their format and required presence but does not authenticate the source.

The frontier uses functional successes and total cost, including failed cases.
A policy dominates another only when its known complete point has at least as
many successes, no more total cost, and a strict improvement on one axis.
Exact ties remain on the frontier. Incomplete points are reported separately;
their unknown outcomes or costs may change the frontier, so the report marks a
partial frontier. Transport and functional outcomes remain separate evidence.

Functional regret is the observed best success (1,000,000) minus the selected
policy's success (0 or 1,000,000). A known success fixes the best value even if
another policy is unknown. If all policies are known failures, the best is zero;
otherwise it remains unknown. Cost regret is reported separately and is only
known when the selected policy passes, all policy outcomes are known, and all
successful alternatives have known costs. An unknown outcome or cost can hide a
cheaper successful alternative, so exact cost regret remains unknown. A failed
selected policy has cost regret `not_applicable`, distinct from unknown or zero.
The report combines neither axis into an invented score and has no effect on
promotion or activation. It reports no confidence interval or paired delta; the
[router value protocol](bench/router-value-protocol.md) plans those for a bench
of fixed arms against the router.
